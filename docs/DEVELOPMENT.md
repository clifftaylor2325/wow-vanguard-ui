# Development

How to build, test and release Vanguard from a clone. [CLAUDE.md](../CLAUDE.md) has the rules every change follows, and [PATTERNS.md](PATTERNS.md) the canonical shapes.

```bash
npm install
npm test          # JS and Lua harness tests under Vitest, once (vitest run, no watch), then a per-area Lua harness summary
npm run test:quick # the JS tests and the Lua smoke tests (both clients, and secret geometry): the fast run while iterating, and the pre-push hook's
npm run test:slot -- <vitest args>  # what npm test runs, with your arguments: e.g. --project lua scripts/tests/chat.test.mjs -t "<name>"
npm run verify    # npm test (real addon Lua in a TEST-ONLY headless WoW client, and the JS tests), then the code-quality scan
                  # (functions of 10 lines or fewer, all documented; colors only from Core/Theme.lua)
npm run coverage  # every test with line coverage of the addon Lua; fails below scripts/lua-coverage-floor.json (100%)
                  # run it on the branch, with main brought in, before its pull request merges: no pull request runs
                  # a test in CI; for now CI runs it only from the Actions tab (no weekly run, no tests in the release run; a hand-started run can ask for a shuffled order with its `shuffle` input),
                  # sharded over parallel jobs (--balanced i/n per job, then --merge <dir> applies the floor once: see CI below)
                  # npm test, npm run test:quick, npm run test:slot and npm run coverage each take a machine-wide test slot first (below)
npm run lint      # luacheck
npm run timing    # the suite on 2 workers (the hosted runner's size): wall time, per-file table; --budget and --baseline fail it
npm run profile -- <area>  # where the Lua of one test area (or "login") spends its time, by file, function and line
npm run bench     # time and Lua instructions per event and per module under a scripted 40-player raid (a harness measurement); --compare <file>; --instr-budget scripts/bench-budget.json fails when a step's addon instructions pass their cap (CI does; the caps are a commit's numbers plus a quarter: lower one when a change speeds a step up, raise one only with the reason in the PR)
npm run media     # regenerate Media/Textures and Media/Icons from scripts/lib/media-sources.mjs (deleting images no source makes)
npm run package   # dist/Vanguard-<version>.zip from committed files
npm run preview   # preview/*.png: the default layout and the options window (needs Playwright)
npm run store-art # dist/store-art/*.png: store, Discord and X banners and logos from the painted crest and the dusk landscape
```

**The Lua engine:** the harness runs the addon on real Lua 5.1.5, the game's Lua, compiled to WebAssembly (`tools/lua51/`, `scripts/lib/lua-wasm.mjs`); that is the default since 2026-11-11 (Cliff). `VG_LUA_ENGINE=fengari` runs any test command on fengari (Lua 5.3 in JS) instead; `npm run bench` and `npm run profile` always run on fengari, whose instruction counts and stack they read. `scripts/tests/README.md` (Two engines) has what to keep in mind so a test reads the same on both.

**One suite run at a time:** a whole run holds one to three gigabytes and every core it can get, and two at once (two clones, two agents, the pre-push hook and a hand-started run) each take twice as long and can exhaust a small machine. So `npm test`, `npm run test:quick`, `npm run test:slot` and `npm run coverage` first take a slot, a lock file in `vanguard-test-slots` in the OS temp folder, shared by every clone on the machine (`scripts/test-slot.mjs`, `scripts/lib/test-slot.mjs`). A machine under 12 GB of memory has one slot and a larger one two; `VG_TEST_SLOTS=n` sets the number and `VG_TEST_SLOT_DIR` the folder. When every slot is busy the run waits (it does not refuse) and prints one line naming each holder's pid, how long it has held the slot, its folder and its command, then a line when it gets a slot. The time it shows is from when the slot was taken, not when the wait began. The lock records the run's pid and, once Vitest has started, Vitest's pid, so a slot stays busy while either runs (killing only the owner does not free it); a slot with neither running is taken over by the next run, and when two runs meet the same dead slot only one gets it; if a pid was reused by another program, the line names the file to delete. Do not start Vitest by hand (`npx vitest`): it skips the slot. A run started from inside a slot (the environment carries `VG_TEST_SLOT_HELD`) does not wait for itself. `npm run timing` starts Vitest itself and does not take a slot.

**Play from your clone:** `npm run link:wow -- --wow "<Forever folder that has Interface/AddOns>"` links `Interface/AddOns/Vanguard` to this clone (a directory junction on Windows, no admin needed), so an edit plus `/reload` shows in game. The folder is remembered in `~/.wow-forever/config.json`, so after the first time it's just `npm run link:wow`. An installed copy is only moved aside with `--replace` (it becomes `Vanguard.backup-<date>`). `--status` shows what's there; `--unlink` removes the link and never deletes a real folder.

[SMOKE-TEST.md](SMOKE-TEST.md) is the in-game checklist to run after a release lands: what to do, what to expect and what to paste back for each step.

**VS Code:** open the folder and accept the recommended extensions: **Lua** (sumneko) and **WoW API** (Ketho), which add Lua 5.1 checking plus autocomplete and docs for the game API. `.vscode/tasks.json` has verify, luacheck (problems show in the editor), coverage, package, preview and link:wow under *Run Task*.

**Windows tools:** `npm run verify` needs only Node. For `npm run lint`, put `luacheck.exe` from the [luacheck releases](https://github.com/lunarmodules/luacheck/releases) on your PATH. CI also runs a Lua 5.1 syntax check (`luac5.1 -p`); you don't need it locally.

**Working with an agent:** `.claude/settings.json` runs `scripts/agent-check.mjs` after every file edit Claude Code makes, so a broken rule (a function over 10 lines, a missing comment, a colour outside the theme, an unguarded hook) is reported at edit time rather than at push. `.claude/skills/` holds a playbook per recurring task (adding a module, a setting, a `/vg` command, media or a client API to the harness; polishing a module; fixing a bug or a visual issue; writing a harness scenario; readying a PR; cutting a release; triaging what the game reports; the weekly PR sweep); `docs/PATTERNS.md` shows the canonical shape of each pattern the rules ask for.

**Text fit:** `scripts/tests/textfit.test.mjs` runs the setup wizard, every options page, the dialogs, the screen at login and unlock mode in a client with the addon's real font widths and every `L[…]` string a third longer (a pseudo-locale, as a translation might run), and fails on text cut short in its box, text running out over an edge of its frame, and text drawn over other text or a control. The overflows it found when it was added are listed in `scripts/tests/textfit-baseline.json`; a new one fails, and so does a listed one that is fixed, so the list only shrinks (`VG_TEXTFIT_WRITE=1 npm run test:slot -- --project lua scripts/tests/textfit.test.mjs` rewrites it after a fix). `scripts/tests/README.md` (Text fit) has how to audit a window of your own.

**Pre-push hook:** `npm install` points git at `.githooks/`, whose pre-push hook runs `npm run test:quick`, `npm run quality`, the baselines check (`scripts/check-baselines.mjs`) and the TOC check, then luacheck and the Lua 5.1 syntax check when they are installed (it names what it skipped; on Windows it always skips the syntax check). It is not the whole suite: that runs before the merge (see Tests before a merge below). `git push --no-verify` skips the hook once.

**Release:** bump `## Version` in `Vanguard.toc` and merge, then run the `release` workflow from the Actions tab on `main` (it tags `v<version>`), or push a matching tag. It runs the raid bench and the checks first (`lua-suite.yml` with `tests: false`: no test runs in the release, so start a full suite on `main` by hand first, or use `scripts/release-local.mjs`), then publishes a GitHub release with the zip. It refuses a tag that is not on `main` and a release whose content checks fail (docs/RELEASING.md). When Actions can't run, or a fix has to go out fast, `node scripts/release-local.mjs` does the same from your machine (a rehearsal by default, `--publish=v<version>` to ship to CurseForge, Wago and GitHub); see `docs/RELEASING.md`.

**Art and fonts:** every texture and icon under `Media/` is made by code in `scripts/lib/media-sources.mjs`: most drawn in plain math (no image editor), the options nav's and minimap's icons and the faction crests rasterized from game-icons.net SVGs in `art/game-icons` (credited in `art/CREDITS.md`); `npm run verify` fails if a committed file doesn't match its source. `node scripts/build-media.mjs --check` also fails on a file anywhere under `Media/` that is neither generated nor named in `FIXED_MEDIA` (the fonts, their licenses and the credit texts), so nothing ships there unseen. The fonts are made from upstream Fira Sans Condensed by `scripts/fonts/make-fonts.py`, and the faction look's heading fonts (Cinzel and Metamorphous, credited in `art/CREDITS.md`) by `scripts/fonts/make-heading-fonts.py` (see those files).

**Testing the addon:** `scripts/tests/<area>.test.mjs` play the addon's real Lua in a headless client built for the tests (`scripts/lib/wow-*.lua`): Lua 5.1 semantics, frames with real layout on a 1920x1080 screen, a world model (units, auras, actions, quests, combat, timers) behind the game API, and mouse and keyboard input. A test sets up the world, acts as the player would, and asserts on what the addon drew. The client also holds the addon to the game's taint rules: a test fails if the addon stores a field on one of the game's frames or touches a protected frame in combat, and it can hide positions and sizes as secrets the way the client does in a fight. The guide is [scripts/tests/README.md](../scripts/tests/README.md).

**Options inventory:** `node scripts/options-inventory.mjs` logs in on both clients in the harness and prints every options page with its tabs, rows, settings with a default, reload rows and modules (`--json <file>` writes one object per row). It is the spike behind [design/SETTINGS-SIMPLIFICATION.md](design/SETTINGS-SIMPLIFICATION.md).

**Code quality:** every function has a comment on the line above it and at most 10 lines of body code, an `ns.On`, `ns.OnUnit` or `ns.Every` outside every function in a file outside `Core/` fails unless `FILE_SCOPE_ALLOWED` in `scripts/lib/code-quality.mjs` lists the file with its count and the reason (a module registers in its `Enable`, through its scope, so the lifecycle can take it down; the list only shrinks), a file that defines a module declaring `live = true` (its own `ns.Module` call, not one it reads with `ns.GetModule`) fails on any `ns.On`, `ns.OnUnit`, `ns.Every`, `T.OnChanged`, `ns.OnMoverPlaced`, `hooksecurefunc` or `:HookScript` of its own outside a `scope:Gate(...)` call (everything goes through the scope), and addon Lua uses no syntax newer than Lua 5.1 (no `goto`, `::label::`, `//`, `&`, `|`, `~` or shifts: the optional fengari engine parses Lua 5.3 and accepts them, the game and the default engine do not); `npm run verify` and CI enforce it on every pull request. `npm run quality` also compiles every file the TOC loads with `luac5.1 -p` when it is installed (`apt-get install lua5.1`) and names the gap when it is not. A secure call (`SetAttribute`, a state driver, an override binding, `ShowUIPanel` or `HideUIPanel`, the SecureHandler forms) outside a combat guard fails `npm run quality` too. `npm run quality` also counts eight report-only patterns (`REPORT_RULES` in `scripts/lib/code-quality.mjs`; `--report` lists them): `OnUpdate` handlers neither throttled nor cleared, frame script handlers (`OnEnter`, `OnShow`, a `HookScript`) that are not `ns.Guard` calls, English literals handed straight to a widget, tooltip, chat line or option row instead of through the string table (`unwrapped-text`) and English joined, chosen or formatted there (`unwrapped-text-shapes`), secret truth tests, pcall results tested for truth, long lines, and table-field functions with no comment; each fails when its count is above or below `scripts/code-quality-baseline.json` (a count that drops lowers the baseline in the same commit), so the baseline only goes down. The shared libraries in `Libs/` stay exactly as upstream wrote them, so the scan, luacheck and the coverage count leave them out.

**Tests before a merge:** no pull request runs a test in CI (Cliff, 2026-11-10). Before a pull request merges, whoever merges it (an agent, usually) brings `main` into the branch and runs `npm run quality` and `npm run coverage` there (every test, both clients, the 100% floor), and the pull request's body says they passed and on which commit. A red local run means no merge. `VG_SKIP_RETAIL=1 npm run coverage` leaves out the Retail-only test files (Retail support is new and best effort) and holds the Lua Forever loads to its own floor, `withoutRetail` in `scripts/lua-coverage-floor.json`, since the Retail branches of shared files go unrun; it is a local shortcut while iterating, not the run before a merge. It does not apply to `npm run coverage -- --merge`, which judges a full set of shards at the `lines` floor whatever the variable says.

**CI:** every pull request gets `verify.yml` ("Quick checks": spelling with typos (`_typos.toml` lists the WoW words it accepts), the code-quality scan, the baselines against the base (`scripts/check-baselines.mjs`: no code-quality, text-fit or options-budget count above the base's), the TOC check (`scripts/check-toc.mjs`: every `.lua` under `Core/`, `Modules/` and `Locales/` listed once, libraries first, the Interface values 16001 and 120105, Title, Version and SavedVariables, and game-type tags the harness reads, `[AllowLoadGameType ...]` and `[ExcludeLoadGameType ...]`, that leave each file on at least one client), luacheck, Lua 5.1 syntax and the release zip, inside a minute; no tests), and `main` requires it to merge. A pull request that changes only docs (`docs/**` and `*.md`) still gets the check, which skips its steps and passes in seconds, so it can merge without a bypass (the spelling check still reads it). A pull request that changes Markdown also gets `markdown.yml` (markdownlint, settings in `.markdownlint-cli2.jsonc`), which is not required. Every action the workflows use is pinned to a commit SHA, with its version in a comment for Dependabot. For now CI runs no tests by itself (Cliff, 2026-11-10): the suite took 45 to 60 minutes as one job, so until Cliff says to turn it back on (sharded CI and the Lua 5.1 engine have merged) the weekly run is off (its cron line waits in a comment in `full-suite.yml`) and `release.yml` calls `lua-suite.yml` with `tests: false`, which runs the raid bench and the checks in front of the publish job, not the tests. The whole suite with the coverage floor and the Retail-only tests runs when it is started from the Actions tab (`full-suite.yml`: *full suite* → *Run workflow*, on any branch); do that on `main` before a release, or use `scripts/release-local.mjs`. `lua-suite.yml` splits the tests over parallel jobs: a plan job reads the `shards` input (12 by default, 1 to 16) and, when the run is shuffled (the weekly run, or a hand start that asks), picks one shuffle seed; each shard job runs `npm run coverage -- --balanced i/n` and uploads its coverage hits and JUnit file (`lua-shard-<i>`); a failed shard fails the run but the others finish (`fail-fast: false`), so the whole failure list is on the run. The split is balanced by measured time, not by file count: `scripts/shard-times.json` holds the seconds each lua-project test file took in a measured run, and the planner (`scripts/lib/shard-plan.mjs`) puts the files longest first into the shard with the least time so far; a file the table has no time for counts as the table's median, so new files spread evenly until the table is refreshed. Every shard computes the same plan from the same checkout (it is deterministic, so no job hands it to another) and runs an explicit list of files with `isolate: false`. Refresh the table after the suite changes a lot, from a finished run: `node scripts/shard-times.mjs --run <run id>` (reads the shard jobs' logs through `gh api`), or `--log <job log>` or `--junit <junit.xml of a shard>` for files you downloaded (any number of sources; a file's time is their mean); `node scripts/shard-times.mjs --print --count 12` shows the plan and its estimated time per shard without writing anything. A test in the quick project (`scripts/shard-plan.test.mjs`) fails when the plan misses or repeats a file on disk, and the merge job fails when a shard's hits differ from its plan. The suite cannot finish faster than its longest file (`options.test.mjs`, about six minutes on a hosted runner) plus about a minute of start-up per job, however many shards there are. Beside the shards, a quick job runs the checks that need no test (code quality, the TOC check, luacheck, Lua 5.1 syntax, the media check, the release zip), then the quick and hooks projects with coverage (uploaded as `lua-shard-quick`), and a bench job runs the raid benchmark with `--instr-budget`. When they have all passed, a last job downloads every job's hits and runs `npm run coverage -- --merge coverage/shards --shards n+1 --plan n`, which runs no test: it fails when a folder is missing or empty, when a test file `vitest list` names has no hits file, or when a file ran twice, in the wrong shard or not at all, merges the hits, and applies the 100% floor once over the merged data (no job alone sees the whole suite, so none judges the floor). The `tests` input (true by default) switches the shard jobs, the quick job's tests and the merge job off together; the bench and the checks still run. `isolate: false` of the lua project holds per shard. The same modes run locally (`npm run coverage -- --balanced 1/4`, then `--merge <folder of lua-shard-<i> subfolders of hits, one per job> --plan 4`), but a local run is one `npm run coverage`. No label makes a pull request run it; the `full-tests` and `preview` labels are retired. The UI preview renders on the weekly run and on a hand-started run that asks for it; it never fails the run (`continue-on-error`): it is a picture to review, not a test. A red weekly run or hand-started run on `main` opens an issue labelled `ci-failure`, which the next green run on `main` closes (a run on another branch reports nothing). The hand-started run takes a `shuffle` input (off by default) that runs the tests in a seeded random order and prints the seed. The repository is public, so standard runners cost no minutes; the gate stays short for the wait, not the bill. Code scanning is GitHub Advanced Security's default setup, configured in the repository's settings rather than a workflow file here; nothing here depends on it.

## Translations

Player text is looked up as `L["English text"]` (`Core/Locale.lua`; the pattern is in [PATTERNS.md](PATTERNS.md)), and `Locales/<locale>.lua` holds one locale's translations for all ten non-English client locales. Each file stops at its first line unless the client runs that locale, so only one locale's text stays in memory.

```sh
node scripts/i18n.mjs extract                 # every key the code looks up, with where
node scripts/i18n.mjs status                  # per locale: translated, missing, orphaned
node scripts/i18n.mjs export deDE deDE.csv    # key, english, translation, context, note
node scripts/i18n.mjs import deDE deDE.csv    # writes Locales/deDE.lua from the translated rows
```

Every row with a translation is imported; the note column (`machine` for a draft, `reviewed` once a speaker has checked it) is for translators. The first translations shipped as machine drafts (Cliff, 2026-10-26) and players' feedback corrects them: a fix goes into the CSV and through `import`, never into the Lua. Volunteers translate through the Localization tab of the CurseForge project; its export comes back as a CSV for the same import. `scripts/i18n.test.mjs` fails when a locale lacks a row for a key the code looks up (a change that adds player text imports a row in all ten, a machine draft at least), when a locale file was edited by hand, keeps a key the code no longer uses, loses a `{placeholder}`, or types a `/vg` command differently from the English (commands, their words and their `<placeholders>` stay English in every language; `import` refuses such a row); `scripts/tests/options.test.mjs` logs in under every locale, so each file's lines run under the coverage floor. Changing a key's English orphans its translations: `status` lists them, and the next import drops them. An options caption whose English ends in ` (reload)` keeps its reload words in a bracket at the end of its translation (half-width or full-width): the options window moves that last bracket into the row's reload tag.

## Releases on CurseForge

`.pkgmeta` tells CurseForge's packager (and Wago's, and the BigWigs packager) what goes in the `Vanguard` folder: exactly what `npm run package` puts in the release zip. `scripts/pkgmeta.test.mjs` fails if the two ever differ, so add a new top-level file or folder to `.pkgmeta`'s ignore list unless players need it.

Both projects exist. `Vanguard.toc` carries `## X-Curse-Project-ID` and `## X-Wago-ID`, and the `listings` job in `release.yml` runs the BigWigs packager after the GitHub release is published, so a new `v*` tag reaches CurseForge and Wago without a manual upload. It needs the repository secrets `CF_API_KEY` (CurseForge, Account → API Tokens) and `WAGO_API_TOKEN` (Wago, Developer tools), and skips itself while either is missing. The packager (v2.6.1, pinned by commit) knows the Forever flavor and maps Interface 16xxx to it. The TOC's second value (120105, Retail 12.1.5) is a retail Interface, so CurseForge lists a release for Retail as well as for Forever (0.8.0 shows under both). Both listings are live and the website links them (`CURSEFORGE_URL` and `WAGO_URL` in its `scripts/lib/html.mjs`).
